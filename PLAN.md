## Только реальные данные (защита от выдумок)

Правило: **каждая цифра и каждый факт в системе берутся из CSV заказчика или из расчёта по ним.** Чего нет в данных — система пишет «в данных нет».

### Как это устроено

1. **ИИ видит только «паспорт фактов».** Python собирает по каждому товару JSON с готовыми фактами: продажи, остаток, заказы в пути, прогноз, рекомендация, дата. Пустые поля записаны явно: `"вес": "нет данных"`. Больше ИИ ничего не получает.
2. **ИИ разрешено не знать.** В промпте прямо: «используй только факты из паспорта; если факта нет — напиши "в данных нет"; не угадывай». Ответ «не знаю» считается правильным, а не ошибкой.
3. **Ответ — строго по форме** (JSON: текст, список использованных фактов, флаг «данных не хватило»). Ответ не по форме отбрасывается.
4. **Код проверяет каждый ответ ИИ:**
   - каждое число в тексте есть в паспорте (с учётом округления);
   - каждая дата и каждый код товара есть в паспорте;
   - нет денег (₽, $, «рублей»): денег в данных нет вообще;
   - нет запрещённых тем, по которым данных нет: вес, контейнеры, названия товаров и поставщиков.
5. **Не прошло проверку** → одна повторная попытка с указанием ошибки → снова не прошло → шаблонный текст, собранный из тех же фактов кодом.
6. **На дашборде видно происхождение текста:** «пояснение ИИ, цифры проверены» или «шаблон, ИИ не прошёл проверку». У каждой цифры есть подсказка, из какого файла и колонки она взята.
7. **Низкая «температура»** (параметр, который делает ответы ИИ менее фантазийными) — 0,2.
8. **Правило и для меня (Claude Code).** В `CLAUDE.md` записано: в README, сводке и сценарии видео — только цифры из итогового файла расчёта `facts.json`. Сценарий видео собирается из этого файла, а не пишется «по памяти».

### Что может пойти не так и что делаем

| Риск | Что делаем |

| **Данные уходят в DeepSeek.** По их политике данные хранятся в Китае и могут идти на обучение моделей, отказ — только письмом на privacy@deepseek.com. | Отправляем минимум: белый список полей (обезличенный код, категория, готовые цифры). Сырые CSV не отправляем никогда. Каждый запрос сохраняем в закрытый журнал — видно, что именно ушло. В видео прямо говорим: для реальных данных энергетики — открытая модель на своём сервере. |
| **CSV попадут в открытый репозиторий.** | `.gitignore` на `*.csv` и папку данных, pre-commit hook блокирует, автотест в CI проверяет. Перед первым push проверяем вручную. |
| **Утечка ключей** (DeepSeek, Telegram, доступ к репозиторию данных). | Только секреты GitHub, в коде и чате ключей нет. gitleaks в pre-commit. Включаем GitHub push protection (блокировка push с ключом). |
| **Логи и артефакты Actions видны всем** в открытом репозитории. | Не печатаем данные и ответы ИИ в лог. Не загружаем сырые данные как артефакты. Публикуем только готовую страницу. |

| **Текст ИИ ломает страницу** (вредный код в ответе). | Текст ИИ вставляется только как текст, с экранированием. Отдельный автотест (этап 6). То же для Telegram. |

| **ИИ или сайт недоступен.** | Запасная цепочка: Pro → Flash → шаблон. При ошибке данных старый дашборд не затирается. |
| **Дашборд публичный.** | Для теста это допустимо: там только обезличенные коды. В реальной компании — вход по почте (например, Cloudflare Access). Пишем это в README. |

**Разрешение пользователя (04.11):** каждую следующую сессию запускает главная сессия сама, но только если предыдущая закончилась с зелёными проверками своего этапа (я проверяю результат сам, не верю одному отчёту). Красные проверки, ошибка или вопрос к пользователю → остановиться и сообщить. Запускать по одной, не параллельно: этапы зависят друг от друга.

**Изменение (04.11, после этапа 2):** этап 3 проверяю, но сессию 5 (этап 4) запускаю только по команде пользователя. Автозапуск по очереди для этапов 4–9 снова включается только если пользователь скажет об этом.

**Разрешение (05.11):** когда сессия 8 (этап 7) закончится, главная сессия сама проверяет результат и, если всё в порядке, запускает сессию 9 (этап 8, финальная проверка). Сессию 10 (видео и сдача) — только по команде пользователя.

Правила для каждой сессии:
1. Начать с чтения этого файла и `.autopilot/` (состояние прогона, `PROGRESS.md`).
2. Делать **только свой этап**. Не заглядывать вперёд и не переделывать прошлые этапы без причины.
3. Закончить, только когда зелёные все проверки своего этапа. Красные — чиним. Не получилось — пишем в `PROGRESS.md`, что именно, и останавливаемся (следующую сессию не запускать).
4. В конце записать в `PROGRESS.md`: что сделано, какие проверки прошли (с результатом), что осталось, что следующему знать.
5. Никаких CSV в git, никаких ключей в чат и файлы. Что должен сделать пользователь, делает только пользователь (раздел ниже).
