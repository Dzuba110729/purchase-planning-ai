# Спецификация: ИИ-система планирования закупок

Глубина `strict`: в спецификации только то, что сказано в `PLAN.md`. Новых возможностей (`A##`) нет. Подробный бриф — `2026-11-04-brief.md`; ни одна цифра отсюда не заменяет его.

## Задача
Импортёру инструментов нужна система, которая по продажам, остаткам и заказам подсказывает, что, сколько и когда закупать. Сдать за 48 часов (до 06.11.2026) в Telegram: ссылка на дашборд, видео и регулярный автоматический запуск. (R01–R03)

## Решение
Python считает все цифры (R05). DeepSeek только пишет тексты, проверяемые кодом (R06, R76). Результат — статичный дашборд на GitHub Pages, пересчёт по расписанию и по загрузке данных, сводка в Telegram (R65, R72, R73). Работа идёт девятью этапами, по одной сессии на этап; этап закрыт только после своих проверок (R04, R78–R82).

## Решения по реализации
- **Python 3.12 + `uv` + pandas + pytest**: так сказано в разделе «Инструменты». Прочие библиотеки (SDK совместимый с форматом OpenAI для DeepSeek, `openpyxl` для Excel, Playwright для проверки страницы) ставит тот таск, которому они нужны.
- **Исходные данные** лежат вне git: папка `share/` (или путь из переменной `DATA_DIR`). В CI их кладёт закрытый репозиторий данных (этап 7).
- **Единый итог расчёта** — `facts.json` (создаёт этап 4): из него берутся цифры для README, сводки, дашборда и сценария видео (R48).
- **ИИ получает только «паспорт фактов»** и возвращает JSON строго по схеме; любая ошибка проверки → шаблон из тех же фактов (R41–R45).
- **Секреты** только в секретах GitHub; в репозитории — имена переменных в `.env.example` (`DEEPSEEK_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `DATA_REPO_DEPLOY_KEY`).
- **Деньги в данных нет**: ни система, ни ИИ не называют сумм в рублях (R19).

## Правила из брифа (перенесены из `PLAN.md`; исполнитель берёт точный текст из таска и брифа)

**Расчёт (этапы 2–4):**
- Дата плана 13.08.2026 (дата выгрузки) — параметр, при новых данных сдвигается сама. Август (неполный месяц) в средние не берётся. (R08, R09)
- Период покрытия — по ритму поставщика: медиана интервала между приходами, в рамках 60–120 дней. (R18)
- Страховой запас по ABC-группе: A — 95%, B — 90%, C — 80%; важность = штуки × дециль цены × наценка. (R20)
- Просроченные заказы, правило 90 дней: до 90 дней — в пути, дата сдвигается на обычное опоздание поставщика; больше — не считаем, список «уточнить у поставщика». (R16)
- Количество округляется вверх до шага партии из истории; нет истории — до 10 шт. (R22)
- Товары с `supply_type = unknown`: плечо = медиана по категории. (R23)
- «Риск излишка»: запаса с учётом заказов в пути хватает больше чем на 12 месяцев. «Риск дефицита»: запас кончится раньше, чем придёт заказ, размещённый сегодня. (R24, R25)
- Наценка < 25% и скоро кончится → список «пересмотр цены» с пометкой «заканчивается». Мёртвые с остатком → список «распродать / вывести». Возвраты вычитаются из спроса. (R26–R28)
- Прогноз = сезонный профиль категории × уровень продаж товара за 12 мес, с исправлением упущенного спроса; проверка — бэктест. (R21)

**ИИ-слой (этап 5):**
- Модели: `deepseek-v4-pro` — главная сводка и проверка аномалий; `deepseek-flash` — короткие пояснения по каждому товару; цепочка Pro → Flash → шаблон; выбор модели — одна настройка в конфиге; адрес API `https://api.deepseek.com`. (R67–R69, R71)
- Температура 0,2. Лимит токенов на запрос и число запросов за запуск. Каждый запрос сохраняется в закрытый журнал. (R47, R58, R49)
- Цифры заказа ИИ не трогает: ИИ советует, человек решает. (R76)

**Дашборд (этап 6):**
- У каждого текста видно происхождение: «пояснение ИИ, цифры проверены» или «шаблон, ИИ не прошёл проверку»; у каждой цифры подсказка, из какого файла и колонки она взята. (R46)
- Красный и жёлтый цвета только для рисков; светлая деловая тема, тёмная автоматически, телефон. (R77)
- Про публичность дашборда: для теста допустимо (только обезличенные коды); в реальной компании — вход по почте, например Cloudflare Access; это пишется в README (этап 8). (R60)

**Регулярный запуск (этап 7):**
- Запуски: по расписанию 04:30 UTC, при загрузке данных в закрытый репозиторий, каждый день, кнопка «запустить сейчас». (R70, R72)
- Telegram-сводка после каждого пересчёта: что заказать, где риск, что изменилось + ссылка. Отправка только в заранее заданный `chat_id`, бот ничего не принимает. (R73, R57)
- Workflow: минимальные `permissions`, версии Actions закреплены по хешу, запуск только по расписанию, push в main и кнопкой владельца, без запуска от чужих pull request. Deploy key — только чтение, на один репозиторий. В логи не печатаются данные и ответы ИИ; сырые данные не загружаются как артефакты; публикуется только готовая страница. (R52–R54)
- При ошибке данных старый дашборд не затирается. (R59)

**Защита (этап 1) и процесс:**
- Перед первым push CSV в репозитории проверяются вручную. В `CLAUDE.md` записано: в README, сводке и сценарии видео — только цифры из `facts.json`. (R50, R48)
- Правила каждой сессии: начать с чтения `PLAN.md` и `.autopilot/`; делать только свой этап; закончить, только когда зелёные все проверки; в конце записать в `.autopilot/PROGRESS.md` что сделано, какие проверки прошли, что осталось. (R78–R82)
- График 48 часов (04.11 вечер — 06.11 день) и порядок сокращения: Excel → Telegram-бот → карточка товара; проверки этапов, дашборд, видео и регулярный запуск не режутся. (R87)

**Видео (этап 9):** Claude пишет сценарий, пользователь записывает экран и озвучивает, без камеры. В видео прямо сказано: для реальных данных энергетики — открытая модель на своём сервере. (R74, R49)

## Вне рамок
Ничего сверх `PLAN.md`. Контейнеры не считаются, бюджет в рублях не считается — это зафиксированные ограничения данных (R17, R19, R29), а не отложенные задачи. Порядок сокращения, если не успеваем: Excel → Telegram-бот → карточка товара (R87).

## Открытые места
- Ключи DeepSeek, Telegram, GitHub — кладёт сам пользователь в секреты GitHub на этапах 5 и 7 (R84, R85). Чат и файлы их не получают.
- Включить push protection в репозитории GitHub — действие пользователя на этапе 1 (R83).
- Видео записывает пользователь (R86).
