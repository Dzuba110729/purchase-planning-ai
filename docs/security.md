# Защита от утечки данных и ключей

Репозиторий открытый, поэтому данные заказчика (CSV) и ключи в него попасть не должны. Защита в несколько слоёв:

1. **`.gitignore`** — игнорирует `*.csv`, `share/`, `.env`, `.env.*` (кроме `.env.example`).
2. **pre-commit** — хук `block-data-files` падает на любом `.csv` (в любом регистре), файле из `share/`, `.env` и `.env.*`; хук `gitleaks` ищет ключи и токены в добавляемых изменениях. Включить: `uv run pre-commit install` (нужен установленный `gitleaks`).
3. **Автотест** `tests/test_repo_guards.py` — `git ls-files` не должен содержать CSV, `share/` и `.env`; `.env.example` — только имена переменных.
4. **CI** (`.github/workflows/ci.yml`) — на каждый push и pull request: тесты, проверка отсутствия CSV в git, gitleaks по всей истории.
5. **Секреты** — только в секретах GitHub (Settings → Secrets and variables → Actions) и в локальном `.env`. В коде, тестах, логах и чате ключей нет.

## Правило про секреты в workflow

Репозиторий открытый: любой код в ветке, которому доступен секрет (например, `DEEPSEEK_API_KEY`), может его прочитать и вывести. Поэтому:

1. Секреты используют только workflow на ветке `main` и ручной запуск владельцем (`workflow_dispatch`).
2. Временные ветки с workflow, которые обращаются к секретам, не создаём. Проверка с ключом идёт на `main`, после просмотра изменений.
3. Единственный workflow с секретами — `run.yml` (пересчёт и публикация): запуск по расписанию, кнопкой владельца; права `contents: read`, `pages: write`, `id-token: write` только на задачу. Без `pull_request`, без артефактов Actions, в логе только счётчики и сообщения «Ошибка …» без значений.
4. Данные лежат в закрытом репозитории `purchase-planning-data`; доступ — deploy key только на чтение (секрет `DATA_REPO_DEPLOY_KEY`), не личный токен. Бот пишет только в заранее заданный `TELEGRAM_CHAT_ID` и ничего не принимает.
5. Workflow `ci.yml` секретов не использует и работает с минимальными правами (`permissions: contents: read`); так должно оставаться. Новый workflow с секретом — только через отдельный просмотр владельцем.

Повод для правила: однажды была создана временная ветка со своим workflow, который читал `DEEPSEEK_API_KEY`, потом ветку удалили. Утечки не было (GitHub скрывает значение секрета в логе), но по такой схеме работать нельзя.

## Включить push protection на GitHub (делает владелец репозитория)

Settings → Code security → Secret protection → Push protection → Enable.

После этого GitHub сам блокирует push, в котором найден ключ. Включите также «Secret scanning» в том же разделе.

## Если ключ всё же попал в git

Считайте его скомпрометированным: отзовите и выпустите новый. Удаление из истории ключ не спасает.
